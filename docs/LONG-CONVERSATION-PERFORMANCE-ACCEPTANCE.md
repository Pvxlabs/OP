# 长对话性能专项：阶段验收

日期：2026-10-21（Asia/Shanghai）。目标：“续接Strategy Host重构”。
契约：[专项 SPEC](LONG-CONVERSATION-PERFORMANCE-SPEC.md)。

## 当前结论

已建立真实会话的三轮空闲、三轮滚动基线，以及较早历史和会话读取专项样本。
在本次窗口与工作负载下，没有复现持续的严重滚动/输入卡死；较早历史出现了短暂
长任务，但所测三个 OP 观察路径不足以解释其时长。不能据此认定所有使用场景正常。

**M2 的归因门禁尚未通过：没有修改采集调度、保护判定或网页渲染策略，
没有“优化后”的性能收益结论。** 本轮代码只增加可重复、手动开启的测量与对应回归。
不以减少采集内容、放宽保护、删除消息节点取得绿色结果。

## 环境与方法

- 入口 HEAD `ce33b462ce6a027430a2c195f579247a61ec0d3b` 加用户现有七个未提交文件。
- 同一 Mac，24 GiB 内存；CEF 154.0.34 / Chromium 154.0.8037.98，原登录/profile/team。
- 真实官方会话，viewport 1280 × 806 CSS px；没有发送消息、查询或派发任务。
- 每轮 30 秒；空闲独立采样。滚动为八次上滚、约 10–15 秒停留、八次下滚；
  完整手势时间在本地 workload.ndjson，不把“上滚次数”当作实际可视页数。
- CEF 进程内 CDP Performance 数值、页面 rAF/long-task/event-loop 数值、0.5 秒进程采样。
  无远程调试端口。探针自身有开销，rAF 不是物理显示帧率，CPU 的 100% 表示一个核心。
- 首个空闲样本只作预热（首次 CDP 起始 metrics 为空）；一次快速滚动探索样本不纳入
  六轮统计。计入样本均具有匹配的会话、可读正文、相同 viewport 和完整 30 秒可见窗口。

三个已测 OP 路径是 collector、mutation handler、completion observer，
不代表全部 OP/CEF/GPU 开销。滚动样本这三者同步耗时占 CDP TaskDuration 的中位数
为 0.33%（分母含测量开销）。进程组峰值 RSS 中位数约 1,178 MiB，包含 browser、
三个 renderer 和 utility，不能作为此会话独占内存。测量时系统内存 free 约 57%。

标准样本中识别到 5 条已挂载回复、约 2,112–2,116 个元素节点；较早历史探索样本
增长至 7 条回复、2,449 个元素节点。这不支持“一次把所有历史全部挂载”的预设，
也不能仅从这些计数证明网页完整的虚拟化实现。

较早历史探索（60 次上滚，单轮）：最大帧间隔 183.4 ms，最长 long-task 168 ms；
collector 单次最大 5.0 ms、累计 17.8 ms，mutation 累计 0.5 ms，completion 累计
0.1 ms。它证明有短暂停顿，尚不足以归因到具体网站函数、布局或 GC。

## 会话读取路径

手动探针读取浏览器已经发生的 Resource Timing，按固定端点类别筛选，只输出
duration/status/字节数量/相对时间，不保存 URL、正文或认证信息，不新增网页 API 请求。

第一次启动中有两条 decoded size 均为 731,569 bytes 的 HTTP 200 会话读取记录，
duration 分别为 3,335.9 ms 和 3,158.7 ms。不能由大小相同推断响应正文完全相同，
并发/重叠请求的时长不能相加，也不是端到端首屏耗时或纯服务端计算时间。

第二次普通刷新中，已记录的会话相关请求包含 HTTP 403，持续约 327–411 ms，
但网页仍能显示目标正文。不能将这些 403 全部归因于主会话读取，不能把正文可见
当作所有官方请求成功。先前故障的 HTTP 500/约 24 秒等待是另一组失败证据。

第三次普通刷新中，731,569 bytes 的 HTTP 200 会话读取耗时 2,703.8 ms。
三次读取专项结束时目标正文均可读；这些采样不能证明实际发送/生成阶段没有卡顿。

## 用户明确场景后的加载专项（M1-L PASS）

用户补充最明显的症状是“打开或刷新时长时间转圈”。因此没有继续扩大滚动优化，
而是增加手动入口“测量本次刷新（最多 60 秒，仅计时）”及“结束刷新计时并保存”。
使用原 profile 的普通 Reload，不清缓存、不额外发请求；跨新文档记录 CEF 被动回调，
有界 128 个数值事件。新文档就绪后启动既有 30 秒成本探针，默认均关闭。
另一次探索样本验证了 60 秒自动结束（实际 60,004.4 ms）；其证据保留，不混入下表。

以下三轮使用最终计时版本、同一目标/窗口/1280 × 806 CSS px，均为可见前台，
samePage、sameConversation、nativeConversationMatched 均为 true，未截断事件。
每轮 30 秒成本探针完整结束，随后手动保存或达到自动上限。时间均从原生刷新起点
计算，只有成本探针起点使用文档自身的 performance 时钟。

| 刷新轮次 | 主文档响应头到达 s | 主文档接收结束 s | 首批回复进入观察器 s | 本地接受耗时 ms | 三条 OP 路径累计 ms / 30 s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.737 | 3.545 | 4.228 | 3.20 | 13.8 |
| 2 | 0.678 | 2.400 | 2.945 | 1.69 | 16.9 |
| 3 | 0.451 | 2.530 | 3.150 | 2.31 | 22.2 |

三轮主文档均 HTTP 200。主文档接收区间包含网络、服务器流式响应及客户端处理，
不能称为纯下载或服务端计算时间。该筛选器没有捕获到会话 GET，不代表页面没有
其他数据请求，也不足以证明官网 SSR/路由实现。不同请求或脚本区间会重叠，不相加。

“首批回复进入观察器”是新文档的非空消息批次到达本地桥接，包含原有 debounce，
不是精确首屏绘制或输入可交互时间；本地接受还经过身份/顺序校验与快照库接受，
也不代表官网已持久化回复。UI 截图确认三轮结束时目标正文均可读、输入框为空，
没有发送消息或查询。另一次网页侧栏打开观察：1.04 秒仍显示原页，7.13 秒观察时
目标正文可读，只能报告此观察区间。刷新样本不替代冷启动/所有打开路径基线。

成本探针分别从文档内 848.9、797.4、554.9 ms 开始，三个 OP 路径累计占 CDP
TaskDuration 约 0.38%、0.46%、0.56%；采样没有覆盖此前的工作，也不代表所有
OP/CEF/GPU 开销。同期网页 long-task 累计 888、754、880 ms，最大 181、171、173 ms；
这些数据不能定位到具体官网函数或 GC，但已测 OP 路径不足以解释这些停顿。

源码检查确认浏览器初始导航只发起一次，刷新只调用一次 Reload，启动不先等待
SQLite 查询再创建浏览器；未发现可以直接修复的重复导航或本地读取阻塞。
本次正常加载等待主要落在主文档接收和网页启动链路；没有复现先前约 24 秒 HTTP 500，
不宣称该故障已修复，也没有证实“缓存爆满”或“所有历史 DOM 一次挂载”。

**M2 决策：不实施猜测性运行时优化。** 已测保护入库仅 1.7–3.2 ms，改保护规则或
移除 DOM 缺乏收益证据。自动显示本地历史会改变现有“官方浏览器优先”的产品契约，
属于另行决策的体验范围，本轮未实现。
